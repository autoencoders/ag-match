 namematch — matching a name against a list, step by step
================================================================================

 Status:        Active — v0.1.0
 Language:      Python 3.12+
 Consumed as:   a library, a copied-in source folder, or a command line program
 Last updated:  2026-09-21

--------------------------------------------------------------------------------
1. WHAT THE COMPONENT DOES
--------------------------------------------------------------------------------

Given one name — typically a company name — and a list you already own, the
component decides which entry of that list, if any, refers to the same
real-world entity. It is built for the cases where ordinary string matching
fails:

  * misspellings and scanning noise     "Acmee Holdngs" -> "Acme Holdings"
  * abbreviations and expansions        "IBM" <-> "International Business Machines"
  * legal-form noise                    "Inc", "Ltd", "GmbH", "SA", "PLC"
  * filler words                        "Group", "Holdings", "International"
  * reordered or dropped words          "Banco Popular de Espana" -> "Popular Banco"
  * accents and transliterations        "Société Générale" -> "Societe Generale"

The list is never copied, indexed or uploaded anywhere. It stays where it
already lives — in memory, in a database, in the data warehouse, behind an
internal service — and the component reaches it through one small search
interface that you implement (§5).

The answer is one of four outcomes: a single matching entry, no match, an
ambiguous result with the candidates named, or an inconclusive result when the
work was cut short by a budget. Every answer arrives with the evidence: which
strings were searched, how many entries each matched, which entries were shown,
and the reasoning behind the verdict.


--------------------------------------------------------------------------------
2. THE IDEA IN ONE PARAGRAPH
--------------------------------------------------------------------------------

The work is split between two parties. The RUNTIME — ordinary, deterministic
Python — generates the first candidates, runs every search, ranks and trims the
results, counts what has been spent and checks the final answer. The LANGUAGE
MODEL does only the two things it is genuinely better at: proposing which short,
distinctive strings are worth searching for a dirty name, and judging whether
two names denote the same entity. The model never sees the list, only the
handful of entries the runtime chose to show it; it cannot search without the
runtime executing the search; it cannot exceed the budgets; and it cannot name
an entry it was not shown.


--------------------------------------------------------------------------------
3. THE PROCESS, STEP BY STEP
--------------------------------------------------------------------------------

This is what happens for one name, in order.

STEP 1 — The request arrives.
  The caller supplies the name to match and, optionally, a small dictionary of
  context (country, sector, city — whatever helps tell namesakes apart). The
  caller has already connected the component to a list by supplying a search
  interface and a one-line description of what that list holds.

STEP 2 — The name is normalized.
  Accents are stripped, case is folded, and whitespace is collapsed. The same
  normalization is applied to the entries of the list on the other side, so
  "Société Générale" and "societe generale" are the same string by the time
  anything is compared.

STEP 3 — The distinctive words are picked out.
  The normalized name is split into words, and the ones that carry no
  identifying information are dropped: legal forms (Inc, Ltd, GmbH, SA, PLC,
  BV, Oy, Pty, ...) and filler (Group, Holdings, International, Global, Services,
  Capital, Bank, and so on), together with anything shorter than three
  characters. What remains — up to three words by default — is what the entity
  is actually called.

STEP 4 — The runtime searches those words on its own, before the model is
         consulted at all.
  Each distinctive word is searched as a plain substring. If the list supports
  approximate search, one further search is run over those words together,
  allowing a small number of letter differences per word. If that comes back
  empty and there was more than one word, the longest word is searched
  approximately on its own — one noisy word should not sink the whole query.
  This is at most five lookups, costs nothing in model usage, and in the easy
  cases it has already found the answer.

STEP 5 — Every set of results is shaped before anyone sees it.
  This applies to the searches in step 4 and to every later one. The runtime
  asks the list for a bounded number of rows (60 by default) plus the true total
  number of matches. It then:
    a. ranks those rows by similarity to the NAME BEING MATCHED — not to the
       search string — using a cheap three-letter-fragment overlap score, so the
       most plausible rows survive the trim;
    b. keeps at most 15 of them;
    c. if the total number of matches is above the "too many" threshold (60),
       attaches a note saying the string matched too much and to try a longer or
       rarer one, while still showing the most similar rows it fetched;
    d. if nothing matched, attaches a note suggesting a shorter fragment, a
       different spelling or approximate search;
    e. drops any entry that has already been shown earlier in this run, passing
       back only its identifier so the same row is never paid for twice;
    f. records the search, its result count, the note and the entries shown in
       a trace that is returned to the caller.

STEP 6 — The opening message is assembled.
  The model is given: how to behave (search short distinctive fragments, ignore
  legal forms and filler, consider abbreviations, translations and reorderings,
  never distinguish entities by punctuation or word order alone); a description
  of what the list holds and which kinds of search it supports; the name to
  match; the context dictionary; a summary of the searches the runtime already
  ran in step 4; and the candidate entries those searches produced. It is told
  not to repeat those searches, and to decide immediately if one of the
  candidates is plainly the entity.

STEP 7 — The model either decides or asks for another search.
  If a candidate is clearly right, or if the distinctive words plainly came back
  with nothing, it answers now and the run is over. Otherwise it proposes a
  further string to search and which kind of search to use — for example the
  correctly spelled version of a word it believes is misspelled, the first few
  letters common to both spellings, an expansion of an abbreviation, or two
  words combined because each is too common on its own. Several searches may be
  requested at once.

STEP 8 — The runtime executes each requested search.
  The string goes to the list through the same interface, and the results come
  back through the shaping of step 5. Three requests never reach the list at
  all: a string already searched in the same way (the model is told it is a
  repeat), an empty string, and any search beyond the budget (the model is told
  to decide with what it has). The default budget is eight searches requested by
  the model; the ones the runtime ran in step 4 are free.

STEP 9 — Narrow, widen, repeat.
  The model reads the new rows and the runtime's note and adjusts: a string that
  matched too much is made longer or rarer, a string that matched nothing is
  shortened, respelled or swapped for a different word. Steps 7 and 8 repeat
  until the model is confident or the budget for model turns (six by default)
  runs out.

STEP 10 — The verdict is written.
  The model states its reasoning first, citing the evidence, and only then
  commits to an outcome: matched (with the identifier of the entry), no match,
  or ambiguous (with the plausible entries listed). It also gives a confidence
  between 0 and 1.

STEP 11 — The verdict is checked before it is accepted.
  The runtime compares the answer against the set of entries actually shown:
    * a match whose identifier was never shown is rejected, and the model is
      asked to answer again, with the valid identifiers listed for it;
    * listed alternatives that were never shown are rejected the same way;
    * an "ambiguous" answer with no alternatives listed is rejected;
    * an identifier attached to a "no match" answer is discarded;
    * an entry named both as the match and as an alternative is removed from the
      alternatives.
  Two such corrections are allowed before the run is given up on. This is what
  makes an invented match impossible rather than merely unlikely.

STEP 12 — The result is returned.
  The caller receives the outcome, the matched entry itself (not only its
  identifier), any alternatives, the full trace of every search — including the
  ones the runtime refused to run and why — every entry that was shown, and the
  usage figures (requests, searches, input and output tokens). If the run ran out
  of turns, or the model never produced an answer that passed step 11, the
  outcome is "inconclusive" and the reason is stated. The component never
  guesses to fill the gap.


--------------------------------------------------------------------------------
4. A WORKED EXAMPLE
--------------------------------------------------------------------------------

List (two entries):

    c1   Acme Holdings International Inc      country=US
    c2   Acme Widgets Ltd                     country=GB

Request: match "Acmee Holdngs Intl." with context {country: US}.

  Step 2   normalized to "acmee holdngs intl."
  Step 3   "intl" is filler and is dropped; distinctive words are
           "acmee" and "holdngs" — both misspelled, neither found in the list
  Step 4   substring search "acmee"   -> 0 matches
           substring search "holdngs" -> 0 matches
           approximate search "acmee holdngs" -> 1 match:
             "acmee" is within one letter of "acme", and
             "holdngs" is within one letter of "holdings"
             -> c1, Acme Holdings International Inc
  Step 5   one row, well under every limit; shown in full
  Step 6   the model is given the name, the context, and c1 as the only candidate
  Step 7   the model answers at once: the distinctive words match after obvious
           typos, the dropped words are filler, and country=US agrees with the
           entry. No further search is requested.
  Step 11  c1 was shown, so the answer is accepted
  Step 12  matched, c1, high confidence, with the three searches in the trace

Note what the misspellings cost: nothing. Substring search alone would have
failed on both words; the approximate search in step 4 recovered the entry
before the model was consulted, and the model then only had to confirm that the
two names denote the same company.


--------------------------------------------------------------------------------
5. CONNECTING YOUR OWN LIST
--------------------------------------------------------------------------------

You supply a small object with:

  * a one-line description of what the list holds and which fields are searched
    — this text is shown to the model verbatim, so make it accurate;
  * a search method taking a string and a maximum number of rows, and returning
    the total number of matches in the whole list plus at most that many rows;
  * optionally, two further methods for the other kinds of search below.

Each row carries an identifier, a name, and a small dictionary of extra fields
(country, city, ticker, ...) used to tell namesakes apart. Methods may be
blocking or asynchronous; blocking ones are run off the main thread. The runtime
detects which methods you implemented and tells the model only about the kinds
of search it can actually use.

Kinds of search

  substring       the whole string appears somewhere in the name, ignoring case
                  and accents
  all words       every word of the string appears somewhere in the name, in any
                  order
  approximate     every word of the string matches some word of the name within
                  a small number of letter differences: none for words of three
                  characters or fewer, one up to five characters, two above that

Approximate search is what recovers misspellings nobody can guess in advance. On
the synthetic evaluation set, substring search alone can surface the right entry
for at most 90% of queries; with approximate search it reaches 100%. If your
list can support it at all, implement it.

Three ways to connect a list are in use:

  in memory        a plain Python list; all three kinds of search included.
                   Approximate search compares word by word in Python, so this
                   suits lists up to a few tens of thousands of rows.

  data warehouse   a ready implementation for BigQuery covering all three kinds
                   of search in SQL. Names are normalized in SQL exactly as they
                   are in Python; the first two kinds use string position, the
                   approximate one uses the warehouse's own edit-distance
                   function word by word. Each search is a single query that also
                   returns the total count. You give it the table, the identifier
                   column, the name column, any extra columns to show the model,
                   any alias columns to search alongside the name, and an
                   optional filter. Every search scans the table, so for large
                   tables store the normalized name in its own column or a
                   materialized view.

  your own         any SQL database, internal service or API. A worked example
                   of about twenty lines ships with the source.

You may also expose additional lookups of your own — a function that returns a
ticker for an identifier, say — which the model may call when an entry needs
further checking.


--------------------------------------------------------------------------------
6. SETTINGS AND DEFAULTS
--------------------------------------------------------------------------------

  setting                default   what it controls
  ---------------------  --------  ----------------------------------------------
  rows shown per search  15        how many entries the model sees per search,
                                   most similar first
  "too many" threshold   60        above this many matches the model is told to
                                   use a narrower string
  rows fetched           = above   how many rows are pulled from the list before
                                   ranking and trimming
  show when too many     yes       above the threshold, still show the most
                                   similar rows rather than nothing
  advance searching      yes       run step 4 before consulting the model
  words searched first   3         how many distinctive words step 4 uses
  search budget          8         searches the model may request (step 4 is free)
  turn budget            6         model turns per run; exceeding it ends the run
                                   as inconclusive
  correction attempts    2         retries when the verdict fails step 11
  sampling temperature   0.0       0 for repeatable answers

Rules of thumb
  * Many near-identical names in the list -> raise the rows shown per search
    before raising the search budget; showing the right row is cheaper than
    another round trip.
  * Very large and very generic lists -> lower the "too many" threshold so the
    model is pushed to use narrower strings sooner.
  * Cost-sensitive batch runs -> keep advance searching on and cut the turn
    budget to three or four; most easy cases are decided on the candidates found
    in step 4.


--------------------------------------------------------------------------------
7. WHAT COMES BACK
--------------------------------------------------------------------------------

  outcome        one of: matched, no match, ambiguous, inconclusive
  identifier     the matched entry's identifier, when there is one
  entry          the matched row itself, with its extra fields
  confidence     0 to 1
  reasoning      one or two sentences naming the evidence
  alternatives   other plausible entries, best first
  trace          every search: the string, the kind, the total number of matches,
                 the entries shown, the runtime's note, and whether it was
                 actually executed
  usage          requests, searches, input tokens, output tokens

"Ambiguous" and "inconclusive" are real outcomes, not errors. Whatever consumes
the result needs a path for them — usually a review queue.

A batch interface matches many names at once with a bounded number running
concurrently (four by default), so a batch cannot overwhelm either the model
provider or your database.


--------------------------------------------------------------------------------
8. COST, LATENCY AND WHAT LEAVES YOUR SYSTEMS
--------------------------------------------------------------------------------

Per name, at the defaults and in the worst case: up to five lookups against your
list before the model is consulted, up to eight more that it requests, inside at
most six model turns. Easy cases finish in a single model turn, because step 4
already found the entry.

What is sent to the model provider: the behavioural instructions, the name being
matched, the context dictionary, and the identifier, name and extra fields of the
rows the runtime chose to show. The list as a whole never leaves your systems,
and the only aggregate disclosed is the number of matches a search produced. Keep
the extra fields small — they are written out for every row shown.

The levers that matter for cost are advance searching (on: fewer turns), the turn
budget, the rows shown per search, and the choice of model.


--------------------------------------------------------------------------------
9. RUNNING IT
--------------------------------------------------------------------------------

Which model. Any of the major providers can drive the process; the default is
Google's Gemini Flash, chosen for cost at this workload. Switching to an OpenAI
or Anthropic model is a one-line change, and the evaluation set (§10) is how you
decide whether a cheaper one is good enough for your list.

Credentials. Two routes reach Gemini: a developer API key held in an environment
variable, or Google Cloud service-account credentials for the enterprise
endpoint. The second accepts a key file, credentials you have already loaded, or
the ambient credentials of the machine — so on a Google Cloud host with a service
account attached, no configuration at all is needed. Project and region fall back
to the usual Google Cloud environment variables. With no credentials anywhere,
startup fails with a message listing every option rather than hanging.

How it is consumed. Three ways: installed as a dependency; copied into an
application as a folder of plain source files; or run as a small command-line
program that matches one name against a CSV file, which is meant for spot checks
rather than batch work.

--------------------------------------------------------------------------------
10. EVALUATION
--------------------------------------------------------------------------------

A seeded synthetic dataset is included: about 130 curated target names, 1,500
filler entries, and 500 queries covering typos, changed legal forms,
abbreviations, reorderings, accents, namesakes that can only be resolved with
context, and three kinds of names that are deliberately absent from the list. A
run scores accuracy, precision, recall, searches per case and tokens per case,
broken down by kind of case, and lists every failure.

Three ways to run it, of which the first two cost nothing:

  * a deterministic fuzzy-string baseline with no model at all — the bar any
    model-driven run has to clear;
  * the full process driven by a scripted stand-in for the model, which
    exercises the runtime without any external calls;
  * a real model, over the whole set or a sample, optionally with different
    settings to test them.

Reports are written as text plus a machine-readable file holding every case, its
verdict, its searches and its token counts. Run the first two before changing
instruction text or defaults: they catch regressions in the runtime rather than
in the model.


--------------------------------------------------------------------------------
11. LIMITS
--------------------------------------------------------------------------------

  * The in-memory approximate search is a Python word-by-word comparison: fine to
    a few tens of thousands of rows, then move the list into a database.
  * The warehouse implementation scans the table on every search unless you
    precompute the normalized name.
  * Matching is lexical — substrings, words, letter differences. The semantic
    leaps (abbreviation, translation, a company known by its founder's name) come
    from the model proposing better strings to search, not from any semantic
    index.
  * Nothing is cached between runs: the same name costs the same twice.
  * One verdict per name, not a scored ranking of the whole list.
  * The model provider sees the rows that were shown. If that is unacceptable for
    a particular list, it cannot be matched this way.


--------------------------------------------------------------------------------
12. GLOSSARY
--------------------------------------------------------------------------------

  entry / row        one item of your list: identifier, name, small set of
                     extra fields
  the list           the data you are matching against, wherever it lives
  search interface   the small object you implement so the runtime can reach the
                     list
  runtime            the deterministic Python around the model: advance
                     searching, shaping, budgets, verdict checking
  distinctive word   a word that is neither a legal form nor filler, at least
                     three characters long
  shown              an entry the model actually received; only these may be
                     named in a verdict
  trace              the record of every search in a run and what it returned
